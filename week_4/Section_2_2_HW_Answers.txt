Exercise 2.2-2 - Selection Sort Analysis with a Loop Invariant
Textbook prompt (CLRS 2.2-2)
- Provide pseudocode for SELECTION-SORT on A[1..n].
- State a loop invariant for the outer loop and prove it by initialization, maintenance, and termination.
- Explain why the outer loop needs only n-1 passes.
- Describe the best- and worst-case running times.

Plain-language restatement
- Picture an assistant who always looks through the unsorted part of a list to find the cheapest remaining item and moves it to the front display. We will explain in plain language how the algorithm works, why the invariant proves it correct, and why its running time stays quadratic no matter the input order.

Step 1 - Pseudocode with 1-based indexing
  SELECTION-SORT(A, n)
    for i = 1 to n - 1
      min_idx = i
      for j = i + 1 to n
        if A[j] < A[min_idx]
          min_idx = j
      if min_idx != i
        swap A[i] and A[min_idx]
- Outer loop chooses the boundary between the sorted prefix A[1..i-1] and the unsorted suffix A[i..n].
- Inner loop scans the suffix and remembers where the smallest number lives.
- A conditional swap moves that smallest number into position i.

Step 2 - State the loop invariant
Informal version: "Before each new pass, the left-hand portion already contains the smallest elements, lined up neatly from smallest to largest."
Formal version: At the start of iteration i, the prefix A[1..i-1] contains the i-1 smallest elements of the original array, in nondecreasing order, and every element in that prefix is less than or equal to every element in A[i..n].

Step 3 - Prove the loop invariant using the three textbook checkpoints
1. Initialization (i = 1): The prefix A[1..0] is empty. An empty sequence is vacuously sorted and trivially contains the "smallest" zero elements. Therefore the invariant holds before the first pass.
2. Maintenance (generic iteration i): Assume the invariant is true when a pass begins. The inner loop scans A[i..n], finds the smallest entry in that range, and stores its index in min_idx. Swapping that element into position i appends the next-smallest value to the prefix. Because no other positions are disturbed, A[1..i] now contains the i smallest elements in nondecreasing order. The invariant is ready for iteration i+1.
3. Termination (loop finishes): The for loop stops after i increases to n. Substituting i = n into the invariant says that A[1..n-1] holds the n-1 smallest elements in sorted order, so the final element A[n] must be the largest. Altogether A[1..n] is sorted.

Step 4 - Why the outer loop stops at n-1
- After we correctly place the first n-1 elements, the lone remaining element automatically belongs in slot n. A final iteration would only compare the last element with itself and swap nothing, so the algorithm avoids that redundant work.

Step 5 - Running-time accounting
1. Comparisons in the inner loop: On pass i the inner loop inspects n-i entries. Summing across passes yields (n-1) + (n-2) + ... + 1 = n(n-1)/2 comparisons.
2. Swaps: At most one swap occurs per pass, so there are at most n-1 swaps.
3. Best case: Even if the array is already sorted, the inner loop still performs the same comparisons, so the cost remains proportional to n^2.
4. Worst case: Completely reversed data triggers the same number of comparisons and swaps, so the cost is still proportional to n^2.
5. Space usage: Only the counters i, j, and the index min_idx are extra -> constant auxiliary space.

Worked example (A = [5, 2, 4, 6, 1, 3])
Pass i | j range scanned | min_idx found | Swap?                | Array afterward
------+-----------------+---------------+---------------------+----------------
1     | positions 2..6  | 5 (value 1)   | swap A[1] with A[5] | [1,2,4,6,5,3]
2     | positions 3..6  | 2 (value 2)   | none                 | [1,2,4,6,5,3]
3     | positions 4..6  | 6 (value 3)   | swap A[3] with A[6] | [1,2,3,6,5,4]
4     | positions 5..6  | 5 (value 5)   | none                 | [1,2,3,6,5,4]
5     | position 6 only | 6 (value 4)   | swap A[5] with A[6] | [1,2,3,4,5,6]
- Before each pass, the prefix matches the invariant statement, and after pass 5 the entire array is sorted.

Quick recap and why it matters
- Core idea: each pass finds the smallest remaining value and locks it into the sorted prefix, using the invariant that the prefix already holds the i-1 smallest values.
- Why it works: the invariant survives initialization, every maintenance step, and termination, so the final array must be sorted.
- When to use: handy for interviews, problems with minimal extra memory, or systems where swapping costs dominate and predictable writes matter.


Exercise 2.2-3 - Linear Search Average-Case Cost
Textbook prompt (CLRS 2.2-3)
- Analyze LINEAR-SEARCH when the target value x, if present, is equally likely to appear in any of the n array positions.
- How many elements does the algorithm inspect on average? What are the best- and worst-case running times?

Plain-language restatement
- Suppose we check a customer roster from top to bottom until we find a name (or report a miss). We want to quantify how many names we expect to check on average in a way that is easy to remember and reuse on homework, LeetCode, or quick code reviews.

Algorithm reminder (1-based)
  LINEAR-SEARCH(A, n, x)
    for i = 1 to n
      if A[i] == x
        return i
    return NIL
- One comparison per position. Stop immediately once we match x; otherwise the loop runs through the entire array and returns NIL.

Step 1 - Define the random variable for "work"
- Let C be the number of comparisons performed.
- If x first appears at position k (1 <= k <= n), then C = k.
- If x is absent, then C = n (we check every element).

Step 2 - Compute the expected number of comparisons when x is present
1. Uniform model: each position k is equally likely with probability 1/n.
2. Expectation formula:
     E[C] = sum_{k=1}^{n} k * P[C = k] = sum_{k=1}^{n} k * (1/n).
3. Factor out 1/n to obtain (1/n) * (1 + 2 + ... + n).
4. Use the triangular-number identity 1 + 2 + ... + n = n(n + 1)/2.
5. Therefore E[C] = (1/n) * n(n + 1)/2 = (n + 1)/2.
6. Interpretation: on average we inspect about half the array. Average-case time therefore grows linearly with n (Theta(n)).

Step 3 - Best and worst cases
- Best case: x is at the first position. C = 1 comparison -> Theta(1) time.
- Worst case: x is absent or at position n. C = n comparisons -> Theta(n) time.
- Average case: as shown, C = (n + 1)/2 in expectation -> Theta(n) time.

Step 4 - Small examples to solidify the story (array [9, 4, 7, 2, 5])
Target | Comparisons examined     | Outcome
-------+-------------------------+---------
x = 9  | check A[1] only         | return 1
x = 7  | check A[1], A[2], A[3]  | return 3
x = 8  | check all five elements | return NIL
- These cases line up exactly with the best-, typical-, and worst-case analyses above.

Quick recap and why it matters
- Core idea: scan left to right until the target appears, tracking that everything before the current index has already been ruled out.
- Why it works: the loop invariant guarantees skipped entries cannot contain x, so the first match is safe and finishing the loop proves absence.
- When to use: great for tiny datasets, debugging utilities, or LeetCode warm-ups when an ordered structure is unavailable.


Exercise 2.2-4 - Forcing a Linear-Time Best Case for Any Comparison Sort
Textbook prompt (CLRS 2.2-4)
- Modify an arbitrary comparison sorting algorithm so that its best-case running time becomes Theta(n) without changing its asymptotic average- or worst-case running times.

Plain-language restatement
- Think of a teammate asking, "If the data is already sorted, can we just recognize that and finish immediately?" We will wrap any sort with a quick pre-check that spots the easy scenario while keeping the usual performance when the input is messy.

Step 1 - Add a fast "already sorted" test
  IS-SORTED(A, n)
    for i = 2 to n
      if A[i] < A[i - 1]
        return FALSE
    return TRUE
- This scan costs Theta(n) time and Theta(1) extra space.

Step 2 - Wrap the original sorting routine
  WRAP-SORT(A, n)
    if IS-SORTED(A, n) == TRUE
      return A                      // done in linear time
    else
      BASE-SORT(A, n)               // run the existing algorithm
      return A
- BASE-SORT is any comparison sort you already trust (insertion sort, merge sort, heapsort, etc.).

Step 3 - Argue about running time
- Best case: if the input is already sorted, IS-SORTED returns TRUE, and WRAP-SORT finishes in Theta(n) time with no further work.
- Other cases: you spend Theta(n) time on the check and then pay the original cost T_base(n). Because every comparison sort already costs at least Omega(n) on nontrivial inputs, the added Theta(n) work does not change its Theta bounds for average or worst cases.
- Space: only a few extra variables for the check -> Theta(1) overhead on top of BASE-SORT.

Step 4 - Concrete traces
Already sorted input (A = [1, 2, 3, 4, 5])
i | Comparison made          | Result
--+-------------------------+--------
2 | A[2] (2) < A[1] (1)?    | no
3 | A[3] (3) < A[2] (2)?    | no
4 | A[4] (4) < A[3] (3)?    | no
5 | A[5] (5) < A[4] (4)?    | no
- IS-SORTED returns TRUE; WRAP-SORT exits after Theta(n) work.

Unsorted input (A = [3, 1, 4, 2])
i | Comparison made          | Result
--+-------------------------+--------
2 | A[2] (1) < A[1] (3)?    | yes
- IS-SORTED stops immediately and returns FALSE. WRAP-SORT then calls BASE-SORT, so the total time is Theta(n) for the check plus the original sorting cost.

Quick recap and why it matters
- Core idea: run a fast linear pass to spot already sorted input, otherwise fall back to the original comparison sort.
- Why it works: the O(n) pre-check does not change average or worst bounds, but it lets truly sorted inputs finish in linear time.
- When to use: valuable in engineering pipelines where data often arrives nearly sorted, in LeetCode variations that reward best-case tuning, or to short-circuit expensive batch sorts.
