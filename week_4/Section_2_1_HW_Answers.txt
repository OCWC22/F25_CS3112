Exercise 2.1-2 — SUM-ARRAY correctness with a loop invariant
Textbook prompt (CLRS 2.1-2)
- State a loop invariant for SUM-ARRAY and use initialization, maintenance, and termination to prove that the algorithm returns the sum of A[1..n].

Plain-language restatement
- Imagine a finance intern adding up every expense in a spreadsheet from top to bottom. We want to prove that the short program below really does produce the same total you would get by adding the numbers manually, no matter how many rows n there are. We will also explain the proof in a way that a non-technical stakeholder can follow.

Given algorithm
  SUM-ARRAY(A, n)
    sum = 0
    for i = 1 to n
      sum = sum + A[i]
    return sum

Step 1 — Translate each line into everyday words
- Start sum at 0 (no money counted yet).
- Visit row 1, then 2, …, up to n.
- On each row i add the number in that row to the running total sum.
- Hand back that running total once every row has been processed.

Step 2 — Pick a loop invariant we can explain to anyone
Loop invariant sentence (informal): “Right before we look at row i, sum already equals the total for all earlier rows.”
Loop invariant sentence (formal): Immediately before iteration i begins, sum = A[1] + A[2] + … + A[i − 1].
Why this is a good invariant:
1. It captures what the running total means at every stage.
2. It only talks about the portion of the table we have already visited, so it is something we can reasonably check.
3. If it holds until the loop finishes, plugging i = n + 1 into the invariant gives the value we want to return.

Step 3 — Prove the invariant in three short checkpoints
1. Initialization (before the first loop iteration, i = 1)
   - sum was set to 0.
   - The “earlier rows” set A[1..0] is empty, and the sum of an empty set is 0 by definition.
   - Therefore the invariant holds before we begin the loop.
2. Maintenance (from one iteration to the next)
   - Suppose the invariant is true when iteration i starts: sum currently equals A[1] + … + A[i − 1].
   - The loop body executes sum = sum + A[i]. Substitute the assumption: sum becomes (A[1] + … + A[i − 1]) + A[i] = A[1] + … + A[i].
   - The for loop then increases i by 1. When the next iteration starts, we are about to process row i + 1, and sum stores A[1] + … + A[(i + 1) − 1], exactly what the invariant claims.
   - No hidden magic happens in between: we never skip a row and the array values stay fixed.
3. Termination (when the loop stops)
   - The loop stops after i reaches n + 1.
   - Substitute i = n + 1 into the invariant: sum = A[1] + A[2] + … + A[(n + 1) − 1] = A[1] + … + A[n].
   - The return statement therefore outputs the total of all entries in the array.

Step 4 — Complexity discussion
- Time cost: There are n iterations. Each performs one addition, one assignment, one loop comparison, and one increment ⇒ Θ(n) time.
- Space cost: Besides the input array, we store only the loop counter i and the running total sum ⇒ Θ(1) extra memory.

Step 5 — Worked example (A = [7, 4, 9], n = 3)
┌─────────┬─────────────────────────────┬────────┬─────────────────────┬─────────┬──────┐
│ i start │ Invariant prediction        │ sum pre│ Body action         │ sum post│ i next│
├─────────┼─────────────────────────────┼────────┼─────────────────────┼─────────┼──────┤
│ 1       │ sum = A[1..0] = 0          │ 0      │ add A[1] = 7        │ 7       │ 2    │
│ 2       │ sum = A[1..1] = 7          │ 7      │ add A[2] = 4        │ 11      │ 3    │
│ 3       │ sum = A[1..2] = 7 + 4 = 11 │ 11     │ add A[3] = 9        │ 20      │ 4    │
└─────────┴─────────────────────────────┴────────┴─────────────────────┴─────────┴──────┘
When the loop exits (i next = 4 = n + 1), the invariant says sum = A[1..3] = 20, which is exactly what is returned.

Key takeaway for the CEO
- The loop invariant acts like a checklist: before each new row we confirm the running total is perfect for everything we have already counted. Because the checklist holds from start to finish, the returned value must be the true grand total.


Exercise 2.1-3 — INSERTION-SORT in decreasing order
Textbook prompt (CLRS 2.1-3)
- Rewrite INSERTION-SORT so that it produces a sequence sorted in decreasing (nonincreasing) order.
- State a loop invariant and prove the modified algorithm is correct.

Plain-language restatement
- We already know the regular insertion sort, which builds an increasing list by inserting each card into its proper position among the cards we have already sorted. Now we want the cards arranged from largest to smallest instead. We will show the exact code change, why it works, and how to explain it to both a professor and a busy executive.

Modified algorithm
  INSERTION-SORT-DECREASING(A, n)
    for i = 2 to n
      key = A[i]
      j = i - 1
      while j > 0 and A[j] < key    // shift smaller items right
        A[j + 1] = A[j]
        j = j - 1
      A[j + 1] = key

What changed from the increasing version?
1. The comparison inside the while loop now uses A[j] < key. We shift numbers that are smaller than the current key to the right, making room for the larger key to move left.
2. Everything else stays the same: we still scan the sorted prefix from right to left and insert the key in its proper spot.

Loop invariant (informal): “Before iteration i starts, the left portion A[1..i − 1] contains the i − 1 largest elements of the array, already arranged from biggest to smallest.”
Loop invariant (formal): At the start of iteration i, A[1..i − 1] is a nonincreasing ordering of the i − 1 largest values from the original input.

Proof of the invariant
1. Initialization (i = 2)
   - The prefix A[1..1] contains just one element, which is trivially sorted and certainly the largest element seen so far. The invariant holds.
2. Maintenance (during iteration i)
   - Inductive assumption: Before iteration i, the first i − 1 positions contain the i − 1 largest elements in nonincreasing order.
   - The while loop compares the key with those elements. Whenever A[j] < key, we shift A[j] one position to the right. Because we only move smaller elements, the relative order of the larger ones (greater or equal to key) remains untouched.
   - When the condition fails we have found the first item that is ≥ key or we have moved past the beginning of the array. Placing key at A[j + 1] inserts it just after those larger-or-equal elements, maintaining the nonincreasing order for the prefix A[1..i].
3. Termination (after the for loop ends)
   - The loop stops when i = n + 1. Plugging into the invariant we conclude that A[1..n] contains all elements in nonincreasing order — exactly what we set out to prove.

Complexity and other properties
- Time: Same as the original insertion sort. Worst-case Θ(n²) comparisons and shifts (when the input is increasing). Best-case Θ(n) when the input is already in decreasing order. Average-case Θ(n²).
- Space: Θ(1) extra storage (temporary key and index j).
- Stability: Yes. Because we only shift elements that are strictly smaller than the key, equal elements keep their relative order.

Worked trace (A = [3, 1, 4, 2])
┌────────────┬────────┬─────────┬─────────────────────────────┬────────────┐
│ Iteration  │ key    │ j start │ while loop details           │ Array      │
├────────────┼────────┼─────────┼─────────────────────────────┼────────────┤
│ i = 2      │ 1      │ 1       │ 3 < 1? no shift             │ [3, 1, 4, 2]│
│ i = 3      │ 4      │ 2       │ 1 < 4 → shift right        │ [3, 1, 1, 2]│
│            │        │         │ 3 < 4 → shift right        │ [3, 3, 1, 2]│
│            │        │         │ place key at A[1]          │ [4, 3, 1, 2]│
│ i = 4      │ 2      │ 3       │ 1 < 2 → shift right        │ [4, 3, 1, 1]│
│            │        │         │ 3 < 2? no; insert key      │ [4, 3, 2, 1]│
└────────────┴────────┴─────────┴─────────────────────────────┴────────────┘
After the loop, the array is [4, 3, 2, 1] — the numbers from largest to smallest. Both the invariant reasoning and the trace agree.

Business-friendly takeaway
- We changed one comparison so the algorithm always keeps the biggest numbers on the left. The loop invariant guarantees that the prefix we have already processed is always perfectly sorted in descending order, so after the last item is inserted the whole list is correct.


Exercise 2.1-4 — LINEAR-SEARCH correctness
Textbook prompt (CLRS 2.1-4)
- Write pseudocode for linear search that scans the array from left to right looking for x.
- Use a loop invariant to prove the code returns an index where x occurs or NIL when x is absent.

Plain-language restatement
- Think of flipping through a paper spreadsheet row by row, comparing each entry with the value you care about. If you ever spot it, you stop and report the row number; if you finish without success you report “not found.” We will write the pseudocode, then justify it carefully.

Algorithm
  LINEAR-SEARCH(A, n, x)
    for i = 1 to n
      if A[i] == x            // check the current row
        return i
    return NIL                // we looked everywhere and never saw x

Loop invariant (informal): “Before checking position i, we already confirmed that x does not sit in any earlier position.”
Loop invariant (formal): Immediately before iteration i begins, x ≠ A[1], x ≠ A[2], …, x ≠ A[i − 1].

Proof using the three invariant checkpoints
1. Initialization (i = 1)
   - The set of earlier positions A[1..0] is empty. It is vacuously true that x is not in an empty set, so the invariant holds.
2. Maintenance (while the loop runs)
   - Assume the invariant is true at the start of iteration i: we have already ruled out positions 1 through i − 1.
   - If A[i] equals x we are done — we return i and satisfy the specification.
   - If A[i] is different from x, we have also ruled out position i. The loop then moves on to i + 1 and the invariant is ready for the next iteration.
3. Termination (after the loop finishes)
   - The loop stops when i = n + 1 because every index 1..n has been checked.
   - The invariant tells us that x is not at any of those indices, so returning NIL is the correct outcome.

Complexity discussion
- Best case Θ(1): the very first element matches x.
- Worst case Θ(n): we must inspect every element (including the “not found” case).
- Average case Θ(n): if x is equally likely to be at any position, the expected number of checks is (n + 1) / 2.
- Space Θ(1): we only track the loop counter i.

Small example (A = [9, 4, 7, 2, 5], x = 2)
┌─────────┬──────────────────────────────┬────────────┐
│ i start │ Invariant guarantee          │ Outcome    │
├─────────┼──────────────────────────────┼────────────┤
│ 1       │ x not in A[1..0] (empty set)│ 9 ≠ 2 ⇒ continue
│ 2       │ x not in A[1]                │ 4 ≠ 2 ⇒ continue
│ 3       │ x not in A[1..2]             │ 7 ≠ 2 ⇒ continue
│ 4       │ x not in A[1..3]             │ 2 = 2 ⇒ return 4
└─────────┴──────────────────────────────┴────────────┘
If x were absent, the final line would read “x not in A[1..5]; return NIL,” matching the invariant statement.

Final message for stakeholders
- Linear search simply checks each position in order. The loop invariant proves that whenever we move past a position we know x is not there. Therefore the first match we hit is safe to return, and if we inspect everything without a match, NIL is the only truthful answer.
