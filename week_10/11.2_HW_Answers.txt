### Problem 11.2-3
**Professor Marley hypothesizes that he can obtain substantial performance gains by modifying the chaining scheme to keep each list in sorted order. How does the professor's modification affect the running time for successful searches, unsuccessful searches, insertions, and deletions?**

**Understanding the Problem:**
Compare standard chaining (unsorted lists) with sorted chaining (keeping each chain sorted by key).

**Analysis:**

**1. SUCCESSFUL SEARCH**

**Unsorted Chaining:**
- Search through chain until key is found
- Average case: Θ(1 + α) where α = n/m
- Must check all elements up to the target

**Sorted Chaining:**
- Search through chain until key is found OR we pass where it should be
- Can stop early if we encounter a larger key
- Average case: Still Θ(1 + α), but with a smaller constant factor
- **Improvement:** Slight improvement in practice (fewer comparisons on average)

**2. UNSUCCESSFUL SEARCH**

**Unsorted Chaining:**
- Must search entire chain
- Average case: Θ(1 + α)
- Must check all α elements in the chain

**Sorted Chaining:**
- Can stop as soon as we encounter a key larger than the search key
- Average case: Θ(1 + α/2) on average (stop halfway through)
- **Improvement:** Approximately 2× faster for unsuccessful searches!

**3. INSERTION**

**Unsorted Chaining:**
- Insert at head of list (or tail)
- Time: O(1) - just add to front
- No search needed

**Sorted Chaining:**
- Must find correct position to maintain sorted order
- Search through chain: O(α)
- Then insert: O(1)
- Total: O(1 + α)
- **Degradation:** Much slower! Goes from O(1) to O(α)

**4. DELETION**

**Unsorted Chaining:**
- Search for element: O(α)
- Delete it: O(1)
- Total: O(1 + α)

**Sorted Chaining:**
- Search for element (can stop early): O(α)
- Delete it: O(1)
- Total: O(1 + α)
- **No significant change:** Both require searching

**Summary Table:**

| Operation           | Unsorted | Sorted  | Change        |
|---------------------|----------|---------|---------------|
| Successful Search   | Θ(1+α)   | Θ(1+α)  | Slight better |
| Unsuccessful Search | Θ(1+α)   | Θ(1+α/2)| ~2× better    |
| Insertion           | O(1)     | O(1+α)  | Much worse    |
| Deletion            | O(1+α)   | O(1+α)  | Similar       |

**Conclusion:**

**When Sorted Chaining is Better:**
- Read-heavy workloads (many searches, few insertions)
- Many unsuccessful searches
- Need to iterate through keys in order

**When Unsorted Chaining is Better:**
- Write-heavy workloads (many insertions)
- Fast insertions are critical
- Most searches are successful

**Professor Marley's Hypothesis:**
The professor is **PARTIALLY CORRECT**:
- ✓ Gains for unsuccessful searches
- ✓ Slight gains for successful searches
- ✗ Significant loss for insertions
- Whether it's a net gain depends on the workload!

**Real-World Consideration:**
In practice, most hash table workloads are write-heavy or balanced, so the O(1) insertion of unsorted chaining is usually preferred. However, for specific read-heavy applications with many unsuccessful searches, sorted chaining could be beneficial.

**Alternative Optimization:**
Instead of sorted lists, consider:
- Using a better hash function to reduce α
- Using a larger table (increase m)
- Using open addressing instead of chaining
- Using self-balancing trees (like red-black trees) for chains when α is large

These alternatives often provide better overall performance than sorted chaining.

---

**Summary of Hash Tables with Chaining:**

**Key Concepts:**
1. **Chaining:** Each slot contains a linked list of elements
2. **Collisions:** Multiple keys hash to same slot → add to chain
3. **Load factor:** α = n/m (average chain length)
4. **Performance:** O(1 + α) for operations

**Advantages:**
- Simple to implement
- Never "fills up" (can always insert)
- Performance degrades gracefully
- Easy to delete elements

**Disadvantages:**
- Extra space for pointers
- Poor cache performance (linked lists)
- Performance depends on hash function quality

**Best Practices:**
- Keep α ≈ 1 (resize when needed)
- Use good hash function
- Insert at head for O(1) insertion
- Consider sorted chains only for read-heavy workloads
